# Wavelength — Full Project Gap Audit

Generated by inspecting the actual codebase (routes, server actions, schema, UI) as of 2026-08-27. This is not based on prior summaries — every finding below was re-verified by reading the real source files. No code was changed, no migrations were run, nothing was committed.

Legend: **Priority** = CRITICAL (breaks the product / blocks launch) · HIGH (real functional gap, should be next) · MEDIUM (real gap, not launch-blocking) · LOW (polish / documented-and-accepted scope cut).

## 5. CRITICAL MISSING FEATURES

These are the items that either break real usage today or represent the biggest gap versus a working, launchable product.

### 5.1 — `next.config.ts` is missing `images.remotePatterns` for the Vercel Blob host
**Status:** CRITICAL — will break the public site's imagery for every real artist.
**File:** `next.config.ts`
**What's happening:** `next/image` refuses to serve/optimize any external image host that isn't explicitly allow-listed. Every real (DB-backed) artist's photos — hero, gallery, band, press, about, video posters — are served from a `*.public.blob.vercel-storage.com` URL via `next/image`. Right now this configuration is entirely empty, so any real artist's public profile will throw `"Invalid src prop... hostname is not configured"` at request time. This has been masked so far because the two demo artists in the repo use static, local `public/artists/...` image paths.
**Fix scope:** a one-line addition to `next.config.ts` (`images.remotePatterns`) — trivial to implement, but must not ship without it.

### 5.2 — No email/SMS notifications anywhere in the booking flow
**Status:** HIGH-CRITICAL for anything marketed as a working booking CRM.
**Files:** `lib/booking.ts`, `lib/admin/bookingActions.ts`
**What's happening:** A new enquiry, a status change to "confirmed," and a new portal-access grant all currently produce zero outbound communication. The only way anyone finds out is by manually opening the admin dashboard. For a platform whose core promise is "artists get booked reliably," this is the biggest functional gap uncovered in this audit.

### 5.3 — No self-service password recovery for artists
**Status:** HIGH.
**What's happening:** An artist who forgets their password is fully locked out until an admin manually resets it via the Portal Access card. There is no token, no email flow, no route.

### 5.4 — No in-app admin user management
**Status:** MEDIUM–HIGH depending on how many admins will be onboarded.
**What's happening:** The 3-role permission system (`super_admin`/`manager`/`editor`) is fully built and enforced everywhere, but the one capability that lets a `super_admin` create/deactivate/re-role another admin has no UI or Server Action — only a CLI script run outside the running app.

## 6. RECOMMENDED NEXT BUILD ORDER

Given limited remaining development time, in priority order:

1. **Fix `next.config.ts` image configuration** (5.1). Trivial effort, launch-blocking severity — do this first, before anything else, regardless of what else gets prioritized.
2. **Add booking-flow email notifications** (5.2): at minimum, an email to the artist/admin on new enquiry, and a confirmation email to the enquirer on submission and on status change to confirmed/rejected. This is the highest-leverage feature gap — it's the difference between "a form that writes to a database" and "a working booking system."
3. **Artist self-service password reset** (5.3): a standard token-based forgot-password flow, reusing the existing bcrypt/session infrastructure.
4. **In-app admin user management UI** (5.4): a simple CRUD screen under `/admin` gated to `super_admin`, using the `canManageAdmins` capability that already exists but has no consumer.
5. **Fix the artist-profile media-ownership gap** (Partially Completed table): validate that a submitted `*MediaId` actually belongs to the acting artist before saving.
6. **Fix the duplicate-render mobile shell issue** (Partially Completed table): render `{children}` once and toggle layout with CSS/conditional wrapper structure instead of two mounted copies.
7. **Nudge/require portal-access creation at approval time** so it's no longer a rememberable-but-forgettable manual step.
8. Everything else in this document (Instagram live feed, cross-artist admin calendar, email verification, forced first-login password change, documentation cleanup) is legitimately lower priority and can wait.

## SUMMARY

**WHAT WE HAVE:** A genuinely mature, mostly-complete platform. The public website, admin CMS (all 13 artist tabs), applications/approval workflow, booking management with automatic calendar blocking, the internal Wavelength calendar (artist + admin, both fully functional), the entire Artist Portal (auth, all 9 CMS tabs, calendar, bookings, account), role-based admin permissions, activity/audit logging, and PWA installability for both portals with a correctly-scoped, privacy-safe service worker are all real, DB-backed, and working — not stubs, not mocks. Data isolation, session handling, and password hashing are all implemented correctly.

**WHAT IS MISSING:** One launch-blocking configuration bug (public images will break for real artists — trivial fix). No email/SMS notifications anywhere in the booking pipeline (biggest real functional gap). No self-service password reset for artists. No in-app way to manage additional admin accounts. A handful of medium/low-priority gaps: media-ownership validation on profile saves, a duplicate-render bug in the mobile nav shells, and some stale documentation.

**WHAT WE SHOULD BUILD NEXT:** Fix the image config immediately (minutes of work, launch-blocking). Then, in order: booking-flow email notifications, artist password reset, and an admin-user-management screen — these three turn the product from "a well-built internal tool" into "a system real external users can rely on without an admin babysitting it."
