# Wavelength — Production-Readiness Audit (3-Day Sprint, Item 5)

Audit performed after items 1–4 (image config, booking email notifications, artist password reset, admin user management) were built and independently verified with `npm run lint` / `npx tsc --noEmit` / `npm run build`. This document covers the full-project security/correctness pass requested as item 5, plus the fixes that were applied as part of it (all re-verified clean afterward).

> **Update (next rapid-build pass):** the three "Flagged, not fixed" items below that were genuinely completable without an architecture change have since been closed — calendar overlap/conflict detection for manual blocks (both admin and artist), new-application admin notifications, and automatic artist portal-credential emails. See each item's note below and the top of `KNOWN_ISSUES.md`/`CALENDAR.md` for what changed. The true concurrent-request race (two simultaneous confirm clicks) remains open, as it requires a database-level exclusion constraint — a schema change, not a bug fix — and is still the one deliberate architectural deferral in this document.

## Fixes applied during this audit

These were found and fixed immediately because each one either broke a feature built in this same sprint or was a concrete, narrowly-scoped security bug — not a redesign, not a new architecture.

1. **CRITICAL — Password reset was completely unreachable.** `proxy.ts`'s artist-route gate only exempted `/artist/login` from its "redirect signed-out visitors" rule. Both new pages (`/artist/forgot-password`, `/artist/reset-password`) fell under the same rule, so a signed-out artist — the only person who would ever use this feature — was bounced to the login page before either page rendered. **Fixed**: both paths added to the public-path allowlist in `proxy.ts`. This means item 3 (password reset) did not actually work end-to-end until this fix; it does now.

2. **HIGH — Stored XSS via JSON-LD on public artist pages.** `app/page.tsx`, `app/artists/[slug]/page.tsx`, and `app/artists/[slug]/shows/page.tsx` all serialize structured data with plain `JSON.stringify()` into a `<script>` tag via `dangerouslySetInnerHTML`. `JSON.stringify` does not escape `<`, so artist-controlled free text (bio, name, show title — none of it HTML-sanitized upstream) containing `</script><script>...` could break out of the JSON-LD block and execute arbitrary script for every visitor to that artist's public page. **Fixed**: new `lib/jsonLd.ts#safeJsonLd()` helper escapes `<` before interpolation; all three call sites updated.

3. **MEDIUM — Unescaped user input in notification email HTML.** `lib/email/templates.ts` interpolated enquirer/artist-supplied strings (client name, message, event details) directly into HTML emails with no escaping — a booking enquiry with HTML in its message field would render as live markup in the recipient's email client. **Fixed**: added an `escapeHtml()` helper, applied to every dynamic value interpolated into an HTML body across all five templates (subjects and the server-generated reset URL were left as-is since they don't need it).

4. **HIGH — Confirming a booking never re-checked availability.** `lib/admin/bookingActions.ts#updateBookingStatusAction` created a `booked_platform` calendar event on confirm without ever re-running `isArtistAvailableOn`, so two enquiries for the same artist/date could both be confirmed by an admin, silently double-booking the artist. **Fixed**: the action now re-checks availability before writing the status change (skipped when the booking already owns its own calendar event, so re-saving an already-confirmed booking doesn't reject against itself) and returns a clear error instead of double-booking. This closes the realistic case — two sequential confirm actions. It does **not** close a true simultaneous-request race (two admins clicking confirm on conflicting bookings in the same instant); that would need a database-level exclusion constraint on the calendar events table, which is a schema/architecture change and was deliberately left for a decision rather than made unilaterally — see "Flagged, not fixed" below.

5. **HIGH — Rejecting an application had no state-machine guard.** `lib/repositories/approvals.ts#rejectApplication` (unlike `approveApplication`) could be called on an already-*approved* application — one that already has a live, linked `artists` row — flipping it to "rejected" while the artist record it spawned kept existing untouched, leaving the two records disagreeing with each other. **Fixed**: added the same kind of status guard `approveApplication` already had; the caller (`lib/admin/applicationActions.ts#rejectApplicationAction`) was also fixed to actually check and surface that result (it previously ignored the repository call's return value entirely).

All five fixes were verified together with a final clean `npm run lint` / `npx tsc --noEmit` / `npm run build`.

## Flagged, not fixed (by design — see reasoning)

- **Residual double-booking race under true concurrency.** The fix above closes the sequential case but not two literally-simultaneous confirm requests. Closing that fully needs a Postgres exclusion constraint (`EXCLUDE USING gist` on artist + date range) or row-level locking around the check-then-write — a schema change, not a bug fix. **Recommendation**: worth doing before heavy concurrent admin usage, not blocking for a 3-day-sprint launch given how rarely two admins would confirm conflicting bookings in the same instant.
- ~~**Manual/external calendar blocks (admin and artist) still don't check for overlap with existing blocks either**~~ — **CLOSED.** `lib/repositories/calendar.ts#getOverlappingBlockingEvents()` now generalizes the same overlap logic `isArtistAvailableOn` already used for a single day to an arbitrary date range, and both `lib/artist/calendarActions.ts` and `lib/admin/calendarActions.ts` now call it before creating or updating a `booked_external`/`unavailable` block, rejecting with a clear "this overlaps an existing block" error instead of silently creating a conflicting one. (`tentative`/`available` still never block anything, unchanged.) While fixing this, also fixed a pre-existing bug in the admin-side update action: editing only an event's start OR end date (not both) previously failed outright because the missing side defaulted to an unparseable empty string instead of the event's own existing value — now matches the artist-side action's correct fallback.
- **Booking form and artist CMS actions validate presence/format but not allowlists or max length** (e.g. `eventType`/`performanceFormat`/`budgetRange` aren't checked against the UI's own option lists server-side, and text fields have no length cap). Combined with fix #2 above, this is no longer an XSS vector, but it's still a data-hygiene gap. Not fixed — this is a broader validation pass across many forms, not a targeted bug, and the sprint's explicit instruction was not to spend time on things that aren't launch-blocking.
- **`media.ownerId` and several `*MediaId` columns still have no FK constraint** (carried over from the prior gap audit, unchanged). Same reasoning as before: a real gap, not launch-blocking, would need a data-backfill-aware migration.
- **`db/schema.ts`'s `calendarFeedToken` comment is stale** (references a deleted ICS-feed route). Dead comment only, zero functional impact. Left as-is per "don't polish minor issues."
- **`lib/repositories/adminUsers.ts` is missing a `server-only` import** that its sibling modules all have. Currently harmless (its only client-side importer does a type-only import, which TypeScript erases), but recommended for defense-in-depth. Left as-is — genuinely cosmetic/preventative, not a live issue.
- **`password_reset_token_hash` has no database index.** Fine at current scale (full-table scan on a small table); worth an index before the artist base grows meaningfully. Not launch-blocking.
- **The "last active admin" / "last active super_admin" protections in `lib/admin/adminUserActions.ts` have a check-then-write race** between two concurrent super_admin sessions. Requires two admins colluding/racing to trigger; low real-world risk given how rarely that scenario would occur. Not fixed.

## Also closed in this pass (from ROADMAP_STATUS.md, not originally part of this audit)

- **New artist applications never notified anyone.** Submitting the public application wizard (`lib/application.ts#submitArtistApplication`) previously wrote the application row and nothing else — no activity log entry, no admin notification of any kind; an admin would only find out by manually checking `/admin/applications`. Now logs an `application.submitted` activity entry and sends admin notification recipients an email (`lib/email/applicationNotifications.ts#notifyNewApplication`, same failure-tolerant pattern as the booking notifications — the application is always fully committed before this runs, and a failed send only logs `application.notification_failed`, never blocks the submission).
- **Admins had to manually relay a new/reset artist password to the artist themselves.** `PortalAccessCard.tsx`'s own hint text used to say exactly that ("Copy this now and send it to the artist"). Now, whenever an admin sets a password (new login or explicit reset) via `setArtistPortalAccessAction`, the artist is automatically emailed their login email + temporary password + a sign-in link (with a "please change this after signing in" note), gated by a checkbox in the form (default checked, so an admin can still opt out and hand-deliver credentials some other way if they prefer). Never sent on an email-only update that left the password unchanged.

## Verified correct (no action needed)

- **Password reset security properties**: raw token is never persisted (only its SHA-256 hash), expiry is enforced on every verification, consuming a token (password change + clearing the hash/expiry columns) happens atomically in one function — genuinely single-use — and a token is scoped to exactly one `artist_users` row by construction, so no cross-artist access is possible. The "forgot password" response is identical whether or not the email matches an account, and all internal errors are swallowed server-side, so account existence cannot leak through this flow.
- **Admin user management authorization**: every action in `lib/admin/adminUserActions.ts` requires `super_admin` + `canManageAdmins`, matching the page-level gate. No privilege-escalation path exists (only an existing super_admin can reach any of these actions at all), self-deactivation is blocked, and the last-admin/last-super-admin protections work correctly outside of the noted race condition.
- **Email notification isolation**: every `sendEmail()` call and its surrounding orchestration in `lib/email/bookingNotifications.ts` is wrapped in try/catch and awaited only *after* the underlying booking/status-change database write has already committed — an email outage can never fail or roll back a booking. Template parameter types are scoped per recipient by construction (no `internalNotes`/`reviewedBy`/`budgetRange` field exists on any artist- or public-facing template's input type), so there is no field to accidentally leak from admin-only data into an artist or enquirer email.
- **Admin and artist authentication/session handling**: both re-verified unchanged and correct — independent cookie/secret spaces, `is_active`/role re-checked from the database on every server-side call rather than trusted from a stale token.
- **Application approval transaction atomicity**: `approveApplication` runs inside a genuine Postgres transaction via a pooled connection; any failure rolls back the whole operation, so a half-created artist record is not possible. Re-approving an already-approved application is (and was) correctly blocked.
- **Image handling**: `next.config.ts`'s `remotePatterns` wildcard for Vercel Blob is correct Next 16 syntax, and no other external image host is reachable through `next/image` anywhere in the app (the one other externally-sourced image field, Instagram post images, only exists in static demo data, never in the database-backed path).
- **PWA / service worker**: the caching allowlist in `public/sw.js` is still strictly limited to static assets (`/_next/static/*`, icons, manifests, the offline page) with zero coverage of `/api/*`, `/admin/*`, or `/artist/*`; the public root layout still references neither manifest nor the service worker.
- **Mobile nav double-render**: confirmed still present in both `ArtistShell.tsx` and `AdminShell.tsx` (unchanged from the prior audit — a known, not-yet-fixed cosmetic/performance issue, not touched in this sprint per "don't redesign working features"). The new admin nav entry (Admin Users, super_admin-only) was confirmed correctly wired into both the desktop and mobile sidebar instances.
- **Environment variables**: every variable read anywhere in source is documented in `.env.example`, and nothing in `.env.example` is unused.
- **Vercel deployment compatibility**: no filesystem writes, no long-lived database connections outside serverless-appropriate pooling, no localhost-only code paths in runtime application code.
- **Build health**: `npm run lint`, `npx tsc --noEmit`, and `npm run build` all run clean as of the final state of this sprint (re-verified independently, not just trusted from earlier steps).
- **No broken routes / no orphaned nav links** — every link in both shells resolves to a real route confirmed present in the build output.

## Bottom line

Two of the fixes in this audit (proxy.ts and the email-notification wiring itself) were required for this sprint's own items 2 and 3 to actually function correctly in production — those aren't optional polish, they're part of finishing the four build items. The XSS and double-booking/rejection-guard fixes are small, contained, non-architectural corrections to real security/correctness bugs uncovered during the audit, applied because they were quick and clearly in scope for "production-readiness." Everything left unfixed is either a genuine architecture-level decision (the concurrency/exclusion-constraint question) or explicitly low-value polish, and is documented above rather than acted on unilaterally.
